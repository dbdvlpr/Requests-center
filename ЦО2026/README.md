# ЦО2026 — Центр интеллектуальной обработки клиентских обращений

Конфигурация 1С:Предприятие 8.3 для компании «ТехноСервис»: приём клиентских обращений по трём каналам, автоматическая классификация и приоритизация с помощью внешней LLM, подбор исполнителя, подготовка черновика ответа и контроль качества решений оператором.

Кейс: Всероссийский IT-марафон «Цифровые инструменты для бизнеса».

- **Платформа:** 1С:Предприятие 8.3, режим совместимости 8.3.25
- **Среда разработки:** 1С:EDT (проект `ЦО2026`)
- **Язык кода:** русский, отступы табуляцией
- **Версия конфигурации:** 1.0.0

---

## 1. Что решает

| Проблема «как было» | Как решено |
|---|---|
| Оператор вручную читает письмо и выбирает категорию | LLM возвращает категорию, срочность и тональность в JSON, 1С сама считает приоритет |
| Приоритет ставится «на глаз» | Формула: срочность текста + вес эмоциональности + ранг контрагента, с текстовым пояснением |
| Исполнитель выбирается вручную | Подбор по тегам компетенций, нагрузке и смежным тегам категории |
| Ответ пишется с нуля | Черновик по номенклатуре (артикулы, остатки, цены) из справочника |
| Качество ИИ не измеряется | Верификация оператором, регистр исправлений, точность модели на панели |
| Персональные данные уходят в модель | Обезличивание почт и телефонов перед отправкой |

## 2. Стек технологий

**Платформа и механизмы 1С**

- Управляемые формы, управляемые блокировки
- HTTP-сервисы (REST) — приём обращений из внешних систем
- Регламентное задание — сбор почты
- `HTTPСоединение` + `ЗаписьJSON`/`ЧтениеJSON` — вызов LLM
- `ЗащищенноеСоединениеOpenSSL` — HTTPS с сертификатами УЦ ОС
- Регистры сведений, виртуальные таблицы, СКД-совместимые запросы
- Роли и права, подсистемы, командный интерфейс

**Внешние сервисы (LLM по REST)**

| Провайдер | Протокол | Авторизация |
|---|---|---|
| YandexGPT | `POST /foundationModels/v1/completion` | `Api-Key` + `x-folder-id` |
| GigaChat | OAuth `/api/v2/oauth` → `POST /api/v1/chat/completions` | `Basic` (ключ) → `Bearer` (токен) |
| Любой OpenAI-совместимый | `POST /v1/chat/completions` | настраиваемая схема |

Библиотека стандартных подсистем (БСП) не используется — конфигурация самодостаточна.

## 3. Поток обработки обращения

```
Почта (IMAP) ─┐
Веб-форма ────┼─► ПринятьВходящее ─► Документ ИОО_Обращение (Новое)
Звонок ───────┘                              │
                                             ▼
                                   Классифицировать (LLM)
                          категория / срочность / тональность / пояснение
                                             │
                        ┌────────────────────┴────────────────────┐
                        ▼                                         ▼
              РассчитатьПриоритет                        ПодобратьИсполнителя
        (срочность + эмоция + ранг контрагента)     (теги компетенций, нагрузка)
                        └────────────────────┬────────────────────┘
                                             ▼
                                     Статус «Назначено»
                                             │
                              ┌──────────────┴──────────────┐
                              ▼                             ▼
                    СформироватьЧерновик            Оператор проверяет
                    (номенклатура из базы)          и подтверждает
                              └──────────────┬──────────────┘
                                             ▼
                                      ОтправитьОтвет
                          (почта / публикация в форме / звонок)
                                             │
                                             ▼
                              ЖурналВызововИИ + ИсправленияКлассификации
```

Ключевой принцип: **LLM предлагает, 1С решает**. Модель не назначает исполнителя и не считает итоговый приоритет — она отдаёт только наблюдения по тексту.

## 4. Модель данных

### 4.1 Справочники

| Справочник | Назначение | Ключевые реквизиты |
|---|---|---|
| `Контрагенты` | Клиенты | контакты, ИНН |
| `Договоры` | Договоры обслуживания | `Контрагент`, `НомерДоговора`, `ДатаНачала`, `ДатаОкончания`, `Действует`, `ПриоритетКонтрагента` |
| `Сотрудники` | Операторы и инженеры | компетенции |
| `Номенклатура` | Запчасти для черновиков | артикул, остаток, цена, описание |
| `УчетныеЗаписиПочты` | Ящики для приёма/отправки | сервер, порт, логин |
| `ИОО_КатегорииОбращений` | Классификатор тем | `ОсновнойТег`, `ТребуетЧерновик`, `Подсказка`, ТЧ `СмежныеТеги` |
| `ИОО_ТегиКомпетенций` | Компетенции для подбора исполнителя | — |
| `ИОО_КаналыОбращений` | Почта / Звонок / ВебФорма | `ВнешнийКод`, `Активен`, `СпособОтветаПоУмолчанию` |
| `ИОО_СтатусыОбращений` | Жизненный цикл | `Порядок`, `Закрывающий`, `ОшибкаОбработки` |
| `ИОО_СтатусыВерификации` | Не проверено / Подтверждено / Исправлено | — |
| `ИОО_СпособыОтвета` | Канал доставки ответа | — |
| `ИОО_УровниЭмоциональности` | Тональность | `Вес` (0..2), `Негативный` |
| `ИОО_ПриоритетыКонтрагентов` | Обычный / Приоритетный / VIP | `Ранг` |
| `ИОО_ПровайдерыLLM` | Технические параметры API | `ФорматПротокола`, `АдресAPI`, `АдресАвторизации`, `СхемаАвторизации`, `ОбластьДоступа`, `Активен` |
| `ИОО_ПрофилиLLM` | Модель + ключ + параметры генерации | `Провайдер`, `КлючAPI` (режим пароля), `ИдентификаторКаталога`, `Модель`, `Температура`, `МаксимумТокенов`, `ТаймаутСекунд`, `КоличествоПримеров`, `ОбезличиватьПередОтправкой`, `ПрофильПоУмолчанию`, ТЧ `Параметры` |

Предопределённые элементы справочников `ИОО_*` — это стабильные точки опоры для кода (`Справочники.ИОО_СтатусыОбращений.Закрыто`) и для запросов (`ЗНАЧЕНИЕ(Справочник.ИОО_СтатусыОбращений.Закрыто)`). Их реквизиты (веса, ранги, адреса провайдеров) заполняются программно в `ДемонстрационныеДанные.ОбеспечитьБазовыеСправочники()`.

### 4.2 Документ `ИОО_Обращение`

| Группа | Реквизиты |
|---|---|
| Регистрация | `ДатаПоступления`, `Канал`, `Источник`, `ВнешнийИдентификатор`, `Тема`, `Текст`, `АдресОтвета`, `Контрагент`, `Договор`, `ПриоритетКонтрагента` |
| Решение ИИ | `Категория`, `СрочностьТекста`, `УровеньЭмоциональности`, `Приоритет`, `ПояснениеПриоритета`, `КатегорияИИ`, `СрочностьИИ`, `УровеньЭмоциональностиИИ`, `ПриоритетИИ`, `ИсполнительИИ`, `ОценкаНазначения`, `ПояснениеНазначения` |
| Исполнение | `Исполнитель`, `Статус`, `СтатусВерификации`, `СтатусЧерновика`, `СпособОтвета`, `ЧерновикОтвета`, `ТекстОтвета` |
| Даты | `ДатаКлассификации`, `ДатаНазначения`, `ДатаОтвета`, `ДатаЗакрытия` |
| Служебные | `КомментарийОшибки`, `ХешТекста`, `Метка`, `Комментарий` |

Пара «`…ИИ` / итоговое» позволяет видеть, что предложила модель и что оставил оператор — на этом строится метрика точности.

Формы документа: `ФормаДокумента`, `ФормаСписка`, `ФормаДиалогаСИИ`.

### 4.3 Регистры сведений

**`ЖурналВызововИИ`** — аудит каждого обращения к модели.

- Измерение: `Идентификатор`
- Ресурсы: `Успех`, `КодСостояния`, `ДлительностьМс`
- Реквизиты: `Дата`, `Обращение`, `Назначение` (тип задачи), `Профиль`, `Модель`, `Промпт`, `Ответ`, `ТекстОшибки`

Промпт и ответ хранятся целиком (до 150 000 символов) — это позволяет разбирать инциденты без повторных вызовов.

**`ИсправленияКлассификации`** — обучающая петля.

- Измерение: `Идентификатор`
- Ресурс: `ИспользоватьВПромпте`
- Реквизиты: `Дата`, `Обращение`, `ТекстОбращения`, `ОтветИИ`, `ИсправленныйОтвет`

Исправления операторов автоматически попадают в промпт как few-shot примеры (`ПримерыДляПромпта`), без дообучения модели.

### 4.4 Перечисления и константы

| Объект | Значения / тип |
|---|---|
| `ИОО_ИсточникиСообщений` | HTTPСервис, ПочтовыйЯщик, РучнойВвод, Импорт |
| `ИОО_ТипыЗадачLLM` | Классификация, Приоритизация, ЧерновикОтвета, Обезличивание, ПроверкаСоединения |

## 5. Программные модули

### `ОбработкаОбращений` (сервер)

Ядро бизнес-логики.

| Метод | Назначение |
|---|---|
| `ПринятьВходящее(Данные)` | Создать обращение из любого канала, защита от дублей по `ВнешнийИдентификатор` |
| `Классифицировать(Ссылка)` | Вызов модели, разбор JSON, расчёт приоритета, подбор исполнителя, авто-черновик |
| `Подтвердить(...)` | Решение оператора, фиксация исправления, смена статуса верификации |
| `СформироватьЧерновик(Ссылка)` | Черновик ответа по номенклатуре с ограничением «только позиции из списка» |
| `ОтправитьОтвет(...)` | Доставка по плану (письмо / публикация / звонок), фиксация даты ответа |
| `СтатусДляПубликации(Номер)` | Публичный статус обращения по номеру (для веб-формы) |
| `РассчитатьПриоритет(...)` | Формула приоритета + текстовое пояснение |
| `ПодобратьИсполнителя(...)` | Скоринг по компетенциям и нагрузке |
| `АктивныйДоговор(...)` | Определение приоритета контрагента по действующему договору |
| `ОбезличитьТекст(...)` | Маскирование почт и телефонов |
| `ХешТекста(...)` | SHA-256 текста — для дедупликации и кэша |
| `Самопроверка()` | Встроенные самотесты алгоритмов |
| `СформироватьПанель(Дней)` | Текстовая панель руководителя (до перехода на дашборд) |

### `ИнтеграцияLLM` (сервер)

| Метод | Назначение |
|---|---|
| `АктивныйПрофиль()` | Профиль из константы → профиль по умолчанию → первый активный |
| `ПараметрыПодключения()` | Единая структура параметров из профиля и провайдера |
| `ВызватьМодель(...)` | Диспетчеризация по формату протокола, журналирование |
| `ПроверитьСоединение()` | Диагностический вызов модели |
| `ВJSON` / `ИзвлечьОбъектJSON` | Сериализация и устойчивый разбор ответа (в т.ч. markdown-обёрток) |

### `РаботаСПочтой` (сервер)

`ПолучитьВходящие()` — разбор почтового ящика, `ОтправитьПисьмо(...)` — отправка ответа.

### `ДемонстрационныеДанные` (сервер)

`Заполнить()` — полный набор демо-данных; `ОбеспечитьНастройкиПоУмолчанию()` — профиль LLM и активная константа; `ОбеспечитьБазовыеСправочники()` — предопределённые элементы; `ОбеспечитьНагрузку()` — обращения за период.

| Объект | Для кого | Что делает |
|---|---|---|
| `НачальнаяСтраница` | все | Навигация, кнопка заполнения демо-данных |

Подсистемы: **«Работа с обращениями»** (документ, справочники, регистры, обработки) и **«Настройки»** (провайдеры, профили, статусы, каналы, учётные записи почты).

## 7. Интеграция с LLM

### Контракт ответа модели

```json
{
  "category": "Ремонт оборудования",
  "urgency": 4,
  "sentiment": "недовольный",
  "keywords": ["насос", "течь"],
  "explanation": "Оборудование не работает, клиент раздражён"
}
```

`category` сопоставляется со справочником категорий, `urgency` ограничивается 1..5, `sentiment` переводится в `ИОО_УровниЭмоциональности`. Невалидный JSON, обрезанный ответ и ошибка HTTP фиксируются в `КомментарийОшибки` и в журнале.

### Настройка

1. `Настройки → Провайдеры LLM` — выбрать предопределённый элемент, проверить адреса и схему авторизации.
2. `Настройки → Профили LLM` — создать профиль: провайдер, ключ API, модель, температура, лимит токенов, таймаут, обезличивание.
3. Константа `АктивныйПрофильLLM` — указать рабочий профиль (если пуста, берётся профиль по умолчанию).
4. Обработка «Настройки подключения» → «Проверить соединение».

Ключ хранится в реквизите с режимом пароля и никогда не пишется в журнал вызовов.

## 8. Алгоритмы

### Приоритет

```
Приоритет = мин(5, СрочностьТекста + ВесЭмоциональности + НадбавкаКонтрагента)

ВесЭмоциональности      = ИОО_УровниЭмоциональности.Вес      (0..2)
НадбавкаКонтрагента     = 1, если Ранг >= 3 И Срочность >= 3, иначе 0
```

Результат сопровождается текстовым пояснением, которое видит оператор: сколько добавила эмоциональность, сколько — ранг контрагента, почему итог такой.

### Подбор исполнителя

```
Балл = 10 × ВесОсновногоТега + 2 × ВесСмежногоТега − 4 × ОткрытыхОбращений
```

Сотрудник без профильных компетенций отсекается (`−1000`). Выбранный вариант и обоснование сохраняются в `ПояснениеНазначения`.

### Обезличивание

Замены по словарю → маскирование e-mail → маскирование телефонов. Применяется, если в профиле включено `ОбезличиватьПередОтправкой`.

## 10. HTTP API

Корень: `/hs/appeals`

**POST `/hs/appeals/create`** — создать обращение.

```json
{
  "текст": "Не работает насос, течёт вода",
  "канал": "ВебФорма",
  "контрагент": "ООО Ромашка",
  "тема": "Протечка",
  "адресОтвета": "client@example.com",
  "внешнийИдентификатор": "web-2026-0001"
}
```

Ответ: `{ "успех": true, "номер": "...", "текст": "..." }`. Повтор с тем же `внешнийИдентификатор` не создаёт дубль.

**GET `/hs/appeals/status?номер=...`** — публичный статус обращения.

## 11. Запуск и демонстрация

1. Открыть проект `ЦО2026` в EDT, обновить конфигурацию БД, запустить клиент.
2. Войти как `Администратор` (создаётся `ДемонстрационныеДанные.ОбеспечитьПользователей`).
3. Открыть «Начальная страница» → «Заполнить демо-данные» — создаются справочники, профиль LLM и обращения за период.
4. «Настройки подключения» → указать ключ API → «Проверить соединение».
5. «Рабочее место оператора» → классифицировать обращение, проверить приоритет и исполнителя, сформировать черновик, отправить.
6. «Панель руководителя» → посмотреть показатели и точность модели.

Встроенная самопроверка алгоритмов: `ОбработкаОбращений.Самопроверка()` возвращает `"OK"` или список расхождений.

## 12. Ограничения текущей версии

- Панель руководителя строится в `ТабличныйДокумент` и не содержит истории — тренды и SLA появятся после введения регистров истории статусов.
- Отчёты на СКД и журнал документов не реализованы.
- Нет регистра истории статусов: «время в статусе» и воронка не считаются.
- Правила SLA заданы неявно (через даты документа), отдельного справочника правил нет.
- Классификация неуверенных случаев обрабатывается через статус `ОшибкаИИ` — без отдельного сценария уточнения.
- Часть проверок EDT сообщает предупреждения по стилю (`SU72` — отсутствие областей, `SU73` — конструкторы структур, `SU81` — чтение реквизитов через точку). На работу не влияют.

## 13. Дорожная карта

| Этап | Содержание |
|---|---|
| 1 | Регистры `ИсторияСтатусовОбращений` и `ПоказателиОбращений`, задание пересчёта |
| 2 | Дашборд руководителя на управляемой форме: KPI-карточки, диаграммы, воронка, тепловая карта нагрузки, drill-down |
| 3 | Справочник `ПравилаSLA` и расчёт просрочек |
| 4 | Сценарий неоднозначных обращений: порог уверенности, повторный разбор, уточняющий вопрос клиенту, эскалация оператору |
